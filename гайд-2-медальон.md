# Гайд 2. Медальонная архитектура: Bronze → Silver → Gold

Продолжение гайда 1. Строим многослойный Lakehouse поверх уже поднятого стека **MinIO → Lakekeeper → Trino**.

Теперь у нас не одна таблица, а **три слоя** (медальон), каждый — свой warehouse, свой бакет в MinIO и свой каталог в Trino. Всё делается руками через UI.

---

## 0. Что такое медальон и что мы строим

**Medallion architecture** — стандартный паттерн, где данные проходят три слоя по мере очистки:

| Слой | Что хранит | Особенность |
|---|---|---|
| **Bronze** (сырой) | данные как пришли, без изменений | только append (дописываем, не перезаписываем) |
| **Silver** (очищенный) | проверенные, приведённые к общей схеме данные | здесь хранится **история** (SCD Type 2) |
| **Gold** (витрины) | готовые агрегаты для бизнеса | готовый ответ на вопрос («сколько продали по магазинам») |

Пример — **продажи и магазины**:

- **Bronze** — 2 сырые таблицы: `raw_sales` (продажи) и `raw_stores` (справочник магазинов).
- **Silver** — 1 таблица `dim_store` с **историей**: если магазин переименовался/переехал, старая версия не удаляется, а закрывается (`valid_from`/`valid_to`/`is_current`).
- **Gold** — 1 витрина `sales_by_store`: продажи, привязанные к **актуальному** магазину, свёрнутые по магазинам.

Схема:

```
              3 бакета                 3 warehouse               3 каталога
  ┌──────────┐ bronze ───► ┌────────────┐ ───► ┌────────┐
  │  MinIO   │ silver ───► │ Lakekeeper │ ───► │ Trino  │ ──► DBeaver
  └──────────┘ gold  ───►  └────────────┘ ───► └────────┘
```

## 2. Шаг 1 — 3 бакета в MinIO (UI)

Открой консоль MinIO: **http://localhost:9001** → логин `minioadmin`, пароль `minioadmin`.

1. Слева в меню: **Buckets**.
2. Кнопка **Create Bucket**.
3. Имя бакета — `bronze` → **Create Bucket**.
4. Повтори то же самое ещё два раза для `silver` и `gold`.

Итог: в списке Buckets должны появиться `bronze`, `silver`, `gold`.

## 3. Шаг 2 — 3 warehouse в Lakekeeper (UI)

Открой UI Lakekeeper: **http://localhost:8181/ui/**

> При самом первом входе Lakekeeper показывает экран приветствия — там нужно **принять Terms of Use** (кнопка «Accept» / «Get started»). Это делается один раз на весь сервер.

Теперь создай **три** warehouse (по одному на слой). В UI это раздел **Warehouses** (или **Catalogs**) → кнопка **Create Warehouse** / **+ New**.

Для каждого warehouse заполни форму одинаково, меняя только **имя** и **бакет**:

| Поле | `bronze` | `silver` | `gold` |
|---|---|---|---|
| **Warehouse name** | `bronze` | `silver` | `gold` |
| **Project** | default (оставь как есть) | default | default |
| **Storage type** | S3 | S3 | S3 |
| **Bucket** | `bronze` | `silver` | `gold` |
| **Endpoint** | `http://host.docker.internal:9000` | то же | то же |
| **Region** | `us-east-1` | то же | то же |
| **Path-style access** | ✓ (включено) | ✓ | ✓ |
| **Flavor** | `s3-compat` | то же | то же |
| **STS enabled** | выключено | выключено | выключено |
| **Access key** | `minioadmin` | `minioadmin` | `minioadmin` |
| **Secret key** | `minioadmin` | `minioadmin` | `minioadmin` |

> ⚠️ **Критично:** в поле **Endpoint** пиши именно `http://host.docker.internal:9000`, а НЕ `http://localhost:9000`. Lakekeeper живёт в контейнере, и `localhost` для него — это он сам, а не твой компьютер.

После создания каждого warehouse он должен появиться в списке со статусом **active**.

> Точные названия кнопок/полей в UI могут чуть отличаться в зависимости от версии Lakekeeper, но состав полей именно такой. Если UI неудобен — то же самое можно сделать через API (см. конец гайда).

## 4. Шаг 3 — каталоги Trino (папка `catalog/`)

Trino узнаёт о warehouse из файлов-каталогов. Мы не монтируем файлы по одному — монтируем **целую папку**, чтобы ты сам мог класть туда свои `.properties` и менять каталоги.

**4.1. Создай рабочую папку и подпапку `catalog/`:**

```bash
mkdir -p catalog
```

**4.2. Создай в `catalog/` три файла** (можно в любом редакторе). Содержимое одинаковое, отличается только имя warehouse в строке `iceberg.rest-catalog.warehouse`.

Файл `catalog/bronze.properties`:

```properties
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=http://host.docker.internal:8181/catalog
iceberg.rest-catalog.warehouse=bronze
iceberg.rest-catalog.nested-namespace-enabled=true
iceberg.unique-table-location=true
fs.native-s3.enabled=true
s3.endpoint=http://host.docker.internal:9000
s3.path-style-access=true
s3.region=us-east-1
s3.aws-access-key=minioadmin
s3.aws-secret-key=minioadmin
```

Файл `catalog/silver.properties` — то же самое, но `iceberg.rest-catalog.warehouse=silver`.
Файл `catalog/gold.properties` — то же самое, но `iceberg.rest-catalog.warehouse=gold`.

> ⚠️ Строка `fs.native-s3.enabled=true` обязательна (это активатор S3-настроек; без неё Trino падает).

**4.3. Пересоздай Trino, смонтировав папку целиком** (выполняй из той папки, где лежит `catalog/`):

```bash
docker rm -f trino
docker run -d --name trino \
  -p 8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog" \
  trinodb/trino:476
```

> 💡 **Почему здесь `docker rm -f` + `docker run`?** Потому что мы меняем сам mount: был один файл `lakekeeper.properties`, стала папка `catalog/` — а mount у уже созданного контейнера поменять нельзя. А вот дальше, если просто **отредактируешь** файл в `catalog/` или **добавишь новый** `.properties` — пересоздавать не нужно, хватит `docker restart trino` (или кнопка Restart в Docker Desktop). Trino читает каталоги при старте.

**4.4. Проверь каталоги** (подожди ~30 секунд, пока Trino поднимется):

```bash
docker exec trino trino --execute "SHOW CATALOGS"
```

Должны появиться `bronze`, `silver`, `gold` (плюс служебный `system`).

## 5. Шаг 4 — увидеть 3 каталога в DBeaver

1. Открой DBeaver → твоё подключение к **Trino**.
2. Обнови дерево (правый клик по подключению → **Refresh**, или F5).
3. В дереве под подключением появятся три «базы данных»: **bronze**, **silver**, **gold**.

Теперь можно писать SQL, обращаясь к любому слою по трёхчастному имени `каталог.схема.таблица`.

> ⚠️ **Почему три части?** В Trino имя таблицы — это `каталог.схема.таблица`. Если написать `bronze.raw_stores` (две части), Trino решит, что `bronze` — это схема, и упадёт с ошибкой «Catalog must be specified». Поэтому всегда пишем полностью: `bronze.lakehouse.raw_stores`. Схему во всех слоях берём одну и ту же — `lakehouse`.

## 6. Шаг 5 — строим слои (SQL в DBeaver)

Выполняй блоки по порядку в SQL-редакторе DBeaver (выдели текст → **Execute**, или Ctrl+Enter).

### 6.1. Bronze — 2 сырые таблицы

```sql
-- схемы (один раз)
CREATE SCHEMA bronze.lakehouse;
CREATE SCHEMA silver.lakehouse;
CREATE SCHEMA gold.lakehouse;

-- сырой справочник магазинов (append-only, хранит историю)
CREATE TABLE bronze.lakehouse.raw_stores (
    store_id   integer,
    store_name varchar,
    city       varchar,
    loaded_at  timestamp
);

-- сырые факты продаж
CREATE TABLE bronze.lakehouse.raw_sales (
    sale_id    bigint,
    store_id   integer,
    product    varchar,
    amount     decimal(10,2),
    sale_date  date
);

-- начальные данные
INSERT INTO bronze.lakehouse.raw_stores VALUES
  (1, 'Магазин на Тверской', 'Москва', TIMESTAMP '2026-09-01 09:00:00'),
  (2, 'Магазин на Невском', 'Санкт-Петербург', TIMESTAMP '2026-09-01 09:00:00');

INSERT INTO bronze.lakehouse.raw_sales VALUES
  (1001, 1, 'Ноутбук', 85000.00, DATE '2026-09-02'),
  (1002, 1, 'Мышь', 1200.00, DATE '2026-09-02'),
  (1003, 2, 'Клавиатура', 3500.00, DATE '2026-09-03'),
  (1004, 2, 'Монитор', 20000.00, DATE '2026-09-03');
```

### 6.2. Silver — измерение магазина с историей (SCD Type 2)

Берём сырой справочник и превращаем его в «медленно меняющееся измерение»: у каждой версии магазина есть `valid_from` / `valid_to` / `is_current`. Оконная функция `LEAD()` берёт дату следующей версии того же магазина:

```sql
CREATE TABLE silver.lakehouse.dim_store AS
SELECT
  store_id,
  store_name,
  city,
  loaded_at AS valid_from,
  LEAD(loaded_at) OVER (PARTITION BY store_id ORDER BY loaded_at) AS valid_to,
  (LEAD(loaded_at) OVER (PARTITION BY store_id ORDER BY loaded_at) IS NULL) AS is_current
FROM bronze.lakehouse.raw_stores;
```

### 6.3. Имитируем изменение магазина (появляется история)

Допустим, магазин 1 переехал и сменил название. В Bronze мы ничего не перезаписываем — просто **дописываем новую строку**:

```sql
INSERT INTO bronze.lakehouse.raw_stores VALUES
  (1, 'Магазин на Арбате', 'Москва', TIMESTAMP '2026-09-10 09:00:00');
```

И пересобираем Silver (теперь у магазина 1 две версии — старая закрыта, новая актуальна):

```sql
DROP TABLE silver.lakehouse.dim_store;

CREATE TABLE silver.lakehouse.dim_store AS
SELECT
  store_id,
  store_name,
  city,
  loaded_at AS valid_from,
  LEAD(loaded_at) OVER (PARTITION BY store_id ORDER BY loaded_at) AS valid_to,
  (LEAD(loaded_at) OVER (PARTITION BY store_id ORDER BY loaded_at) IS NULL) AS is_current
FROM bronze.lakehouse.raw_stores;
```

Посмотри на историю:

```sql
SELECT * FROM silver.lakehouse.dim_store ORDER BY store_id, valid_from;
```

Ожидаемый результат — у магазина 1 две строки:

| store_id | store_name | valid_from | valid_to | is_current |
|---|---|---|---|---|
| 1 | Магазин на Тверской | 2026-09-01 | 2026-09-10 | false |
| 1 | Магазин на Арбате | 2026-09-10 | (null) | true |
| 2 | Магазин на Невском | 2026-09-01 | (null) | true |

### 6.4. Gold — витрина (join продаж с актуальным магазином)

Считаем выручку по магазинам, привязывая продажи к **актуальной** версии магазина (`is_current = true`):

```sql
CREATE TABLE gold.lakehouse.sales_by_store AS
SELECT
  d.store_name,
  d.city,
  COUNT(*)      AS sales_count,
  SUM(s.amount) AS total_amount
FROM bronze.lakehouse.raw_sales s
JOIN silver.lakehouse.dim_store d
  ON s.store_id = d.store_id AND d.is_current = true
GROUP BY d.store_name, d.city;
```

Проверь:

```sql
SELECT * FROM gold.lakehouse.sales_by_store;
```

| store_name | city | sales_count | total_amount |
|---|---|---|---|
| Магазин на Арбате | Москва | 2 | 86200.00 |
| Магазин на Невском | Санкт-Петербург | 2 | 23500.00 |

Обрати внимание: продажи магазина 1 теперь привязаны к **«Магазин на Арбате»** (актуальное имя), а не к старому «Тверской». В этом смысл SCD Type 2 + джоина с `is_current`.

## 7. Проверка: где лежат данные в MinIO

Открой консоль MinIO (http://localhost:9001) и загляни в бакеты:

- **`bronze`** — папки `raw_stores-…/` и `raw_sales-…/` с `data/*.parquet`.
- **`silver`** — папка `dim_store-…/`.
- **`gold`** — папка `sales_by_store-…/`.

Каждый слой — физически отдельный бакет. Это и есть медальон: данные физически разделены по слоям, а не лежат в одной куче.

## 8. Если что-то пошло не так

- **`Catalog must be specified when session catalog is not set`** — ты написал двухчастное имя. Пиши три части: `каталог.схема.таблица`.
- **Warehouse создаётся, но Trino его не видит** — проверь, что в `.properties` строка `iceberg.rest-catalog.warehouse` совпадает с именем warehouse, и что Trino пересоздан после добавления файлов.
- **Кириллица в данных как «????»** — это бывает только при запуске SQL через консоль `trino` без UTF-8 локали. В DBeaver (JDBC) всё сохраняется корректно. Для консоли добавляй `-e LANG=C.UTF-8 -e LC_ALL=C.UTF-8` к `docker exec`.
- **`host.docker.internal` не резолвится** (Linux) — добавь `--add-host host.docker.internal:host-gateway` к команде `docker run` (и в endpoint warehouse используй реальный IP хоста).
- **Забыл пароль/порт** — шпаргалка в гайде 1, §2.

## 9. Остановить и удалить всё

Все слои живут в тех же контейнерах и томах, что и в гайде 1 (бакеты `bronze`/`silver`/`gold` и все таблицы лежат внутри тома `minio-data`):

```bash
# 1. Контейнеры (флаг -f останавливает и удаляет сразу)
docker rm -f trino lakekeeper lakehouse-pg lakehouse-minio

# 2. Данные (тома) — сюда входят все бакеты и таблицы всех слоёв
docker volume rm minio-data pg-data

# 3. Образы (скачаются заново при следующем запуске)
docker rmi trinodb/trino:476 \
          quay.io/lakekeeper/catalog:latest-main \
          postgres:17 \
          pgsty/mc:latest \
          pgsty/silo:latest
```

Проверка: `docker ps -a`, `docker volume ls`, `docker images` не должны показывать ни один из этих элементов. Чтобы просто приостановить — `docker stop` без `rm`.

## Приложение: то же самое через API (если UI не нужен)

Warehouse можно создать не в UI, а запросом (порт `management` у Lakekeeper). Для слоя `bronze`:

```bash
curl -X POST http://localhost:8181/management/v1/warehouse \
  -H "Content-Type: application/json" \
  -d '{
    "warehouse-name": "bronze",
    "project-id": "00000000-0000-0000-0000-000000000000",
    "storage-profile": {
      "type": "s3",
      "bucket": "bronze",
      "key-prefix": "",
      "endpoint": "http://host.docker.internal:9000",
      "region": "us-east-1",
      "path-style-access": true,
      "flavor": "s3-compat",
      "sts-enabled": false
    },
    "storage-credential": {
      "type": "s3",
      "credential-type": "access-key",
      "access-key-id": "minioadmin",
      "secret-access-key": "minioadmin"
    }
  }'
```

Для `silver` и `gold` — меняешь `warehouse-name` и `bucket` на `silver`/`gold`.
